Проблема и аудитория

Ошибочные метки в обращениях клиентов ухудшают обучающий набор классификатора. Команда разметки тратит время на повторный просмотр всего CSV. Цель прототипа - выбрать наиболее полезные строки для ручной проверки и показать проверяемое основание рекомендации.

Пример: «Не могу войти после смены пароля» размечено как «Доставка». Система предлагает «Аккаунт» и показывает цитату. Сообщение сразу о доставке и оплате передается человеку без принудительного выбора одной метки.

Что предъявляется на КП2

| Готово и проверено | Еще не подтверждено |
| --- | --- |
| Пять отдельных модулей агентов, локальный интерфейс, очередь, обратная связь, журнал и экспорт | Качество живой LLM и выигрыш пяти агентов на реальных данных |
| 120 синтетических примеров, воспроизводимая оценка на 48 строках, 29 автоматических тестов | Независимая экспертная разметка, личные коммиты участников и согласование новой темы |

Самооценка: работающий инженерный прототип с первыми проверяемыми результатами. Исследовательская часть и подтверждение индивидуального вклада остаются открытыми. Все опубликованные метрики относятся к эвристическому демо без LLM.

Каждый участник отвечает за собственного агента. Оркестратор связывает отдельные решения через общее состояние; агенты не являются пятью названиями одного запроса.

| --- | --- | --- |
| Ковалев Илья Инструкция | Проверяет определения и пересечения; формирует вопросы к инструкции | Спецификация, версия, хеш, issues/questions |
| Беседин Артем Семантика | Сопоставляет текст с классами; выбирает один/несколько классов или воздержание | Метки, дословная цитата, запрос соседей |
| Подылов Роман Согласованность | Находит top-4 по символьному TF-IDF; проверяет значимость разных меток | Конфликт, ID соседей, обоснование |
| Хримян Артур Арбитр | Сопоставляет выводы; может вызвать один повтор семантической проверки | keep / change / review / recheck |
| Курилов Максим Очередь | Выбирает случаи при бюджете; после ответа человека выбирает связанную группу | Очередь, журнал решения, повторная проверка группы |

Маршрут

CSV + инструкция → агент инструкции → семантика → согласованность и поиск соседей → арбитр → агент очереди → человек. После ответа человека повторно проверяется связанная группа; арбитр может вернуть отдельный случай на один пересмотр.

Стек и роль LLM

Python 3.10+, стандартная библиотека, локальный HTTP-интерфейс, JSON/CSV, символьный TF-IDF. Числа и метрики считает код. В режиме llm смысл и разногласия оценивает выбранная модель через совместимый Chat Completions API. В режиме demo те же контракты реализованы правилами.

Это фиксированный workflow с условными переходами. Общая модель в разных ролях может повторять одну ошибку. JSON, цитаты, ID, бюджет и число повторов проверяются программно. Полная схема и контракты находятся в docs/ARCHITECTURE.md.

Реализовано сейчас

Прием CSV и проверка схемы; пять агентных модулей; поиск соседей; арбитраж; приоритетная очередь; подтверждение человеком; повторная оценка группы; экспорт; промпты и API-адаптер; тесты и код оценки.

Отклонения и причины

Исходная предметная область заменена. Собственная модель не обучается. LangGraph, PostgreSQL и embeddings отложены: для КП2 достаточно малого локального набора. Живой LLM-прогон не выполнен из-за отсутствия настроенного доступа к модели; его результаты не подменены эвристическими.

Приведенные октябрьские даты - план из исходной презентации. Это не утверждение о датах выполнения новой реализации.

Данные и первые измерения

Набор содержит 120 синтетических обращений: 100 однотемных и 20 спорных/непрофильных. В 24 однотемных примерах программно заменена метка. Seed: 20261105. Независимой экспертной проверки эталонов пока нет.

Разделение: 72 строки dev и 48 test, по семействам парафраз. В test: 10 внесенных ошибок, 8 спорных/непрофильных строк, 30 чистых. Это отдельная проверочная часть синтетического набора, а не независимый закрытый реальный тест.

| Метод | Полезных из 20 | Ошибок из 20 | Recall ошибок в top-20 |
| --- | --- | --- | --- |
| Случайная очередь¹ | 7,46 | 4,11 | 0,411 |
| Противоречия соседей | 12 | 9 | 0,900 |
| Ключевые слова | 18 | 10 | 1,000 |
| Пять агентов, demo | 18 | 10 | 1,000 |

¹ Среднее по 100 перестановкам с seed 0–99. Для остальных методов порядок воспроизводим. Источник всех чисел: results/kp2_demo/metrics.json.

Определения метрик

**Полезный случай** - внесенная ошибка либо заранее выделенная неоднозначность/непрофильный текст. Precision@20 по полезным случаям = 18/20 = 0,90. Precision@20 именно по ошибкам = 10/20 = 0,50. Recall ошибок @20 = 10/10 = 1,00.

Доля предложенных изменений чистых меток: 0/30 в demo. Этот ноль на малом искусственном наборе не доказывает безопасность массового изменения. Изменения в исходник автоматически не вносятся.

Вывод эксперимента

Пять агентов и ключевые слова дали одинаковый результат в top-20. Выигрыш мультиагентного подхода не доказан. Для следующего опыта нужны реальные расхождения разметчиков, отрицания, близкие классы и независимый одиночный LLM baseline при том же бюджете.

Эталоны находятся отдельно в evaluation/gold.json и читаются только оценщиком после завершения аудита. Вход агентов содержит лишь id, text, label и инструкцию.

Демонстрация и воспроизведение

Снимок ниже получен из работающего интерфейса на полном учебном наборе из 120 строк. Это демонстрационный запуск; численные метрики на предыдущей странице относятся к отдельным 48 проверочным строкам.

Сценарий

Загрузить CSV → запустить проверку → открыть строку → сопоставить цитату и соседей → подтвердить метку → увидеть новую очередь → выгрузить рекомендации или CSV с ручными исправлениями.

Команды из корня архива

python -m label_audit serve --open
python -m unittest discover -s tests -v
python -m label_audit evaluate --out runtime/evaluation

Достаточно Python 3.10+, зависимости для запуска приложения не устанавливаются. В Windows есть START_DEMO.bat и REPRODUCE.bat. Состояние каждого веб-запуска сохраняется в runtime/runs/; исходный CSV остается неизменным.

Для LLM задать LLM_BASE_URL, LLM_MODEL и при необходимости LLM_API_KEY. Сначала проверить 8 строк с лимитом 40 обращений. Полная инструкция находится в README.md; ключи в архив не включаются.

Лимиты и наблюдаемость

Не более 500 строк по 4000 символов. Дословность цитат, известность меток и ID, числовые границы confidence, бюджет очереди и максимум одного повторного разбора контролируются кодом. Временные сетевые ошибки допускают один повтор; каждая попытка расходует лимит обращений. При исчерпании лимита запуск прекращается с явной ошибкой.

Кэш привязан к endpoint, модели, промпту и данным. Токены берутся из usage провайдера. Если usage или тарифы отсутствуют, стоимость равна null. Повтор из кэша не считается новым API-запросом. Размер денежного бюджета не задается числом обращений.

Главные риски

**Синтетика:** простые ошибки завышают качество. **Общая модель:** агенты могут соглашаться в неверном выводе. **Поиск:** схожий текст может иметь другое намерение. **Инструкция:** пересечение классов нельзя исправить голосованием. **Стоимость:** несколько проверок могут не дать улучшения.

Известный трудный случай: «Доставка уже в порядке, проблема только с оплатой». Эвристика замечает две темы и отправляет строку человеку, хотя актуальное намерение одно. На подобных примерах требуется измерить реальную пользу LLM.

Ограничения локального прототипа: нет многопользовательской авторизации, промышленного развертывания и гарантии сохранения сессии в интерфейсе после перезапуска сервера. Файлы предыдущих запусков сохраняются. Публичный сервер не требуется условиями курса.

Исследовательский вопрос

Позволяют ли инструкция, проверка соседей и арбитраж найти больше реальных ошибочных меток в первых 20 проверках, чем одиночный LLM, при сопоставимом расходе API? Плановый ориентир precision@20 по ошибкам ≥0,80 требует минимум 16 реальных ошибок в наборе и не переносится автоматически на текущую синтетику.

Самооценка на КП2

**Инженерная часть:** сквозной локальный сценарий работает, результаты воспроизводимы, роли разделены. **Оценка качества:** проведена только проверка на синтетике; преимущество над простым baseline не найдено. **Готовность к финалу:** нужны живые измерения, человеческие эталоны, подтвержденные личные доработки и согласование новой темы.
